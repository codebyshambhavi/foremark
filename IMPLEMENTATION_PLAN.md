**Goal:** one reliable, well-presented workflow, not the most features. If a feature threatens it, the feature is cut.

## The workflow that must work (acceptance scenario)

1. Worker submits a voice or text safety report.
2. Prisma transcribes the audio (a real API call).
3. Reporter edits/confirms and submits.
4. Safety officer reviews it and accepts it into a case.
5. Officer assigns a corrective action.
6. Assignee uploads evidence and submits for verification.
7. Officer verifies; the action becomes **Verified Closed**.
8. A later, similar report is submitted.
9. The Safety Memory Engine retrieves the earlier case and explains why.
10. Officer reviews the earlier action, evidence and verification history, then confirms or rejects the relationship.
11. The case timeline and investigation record update.
12. Everything persists after a page refresh.

Each batch below ends with a stated verification. **"Verified" means I ran it and saw the result; anything else is labelled untested.**

## Windows 11 reproducibility rules (apply to every batch from Batch 2)

The maintainer develops on **Windows 11 with VS Code, PowerShell and Git for Windows**. My sandbox is Linux, so Windows-only
failures cannot be observed directly; these rules exist to prevent them, and anything I cannot confirm on Windows is labelled.

1. **Commands are PowerShell-first**, run from the repo root, using `py -3` and the virtual-environment interpreter directly
   (`backend\.venv\Scripts\python.exe -m pytest`). No reliance on `make`, bash, `curl` (an alias in PowerShell), `<` redirection, or `source`.
2. **No script-activation dependency.** Documentation never requires `Activate.ps1` (blocked by default execution policy).
3. **Every text file is read and written with an explicit `encoding="utf-8"`.** Python on Windows defaults to a legacy code page,
   which corrupts Hindi. Enforced with the `ruff` rule `PLW1514` in the lint step, plus tests that round-trip Devanagari.
4. **UTF-8 BOM and CRLF tolerated** wherever users edit files by hand (`.env`, reference transcripts); `.gitattributes` keeps the repo LF.
5. **Dependencies must have Windows wheels.** Pinned in `requirements.txt` (psycopg 3 `[binary]`, argon2-cffi, etc.). No `python-magic`
   (needs a native library on Windows); content sniffing is pure Python. `tzdata` is a dependency because `zoneinfo` has no
   system timezone database on Windows.
6. **Timezone independence.** All stored times are UTC; tests inject a clock and never depend on the machine's timezone (the maintainer is in IST).
7. **Paths:** storage keys always use `/`; local files are addressed through `pathlib`; user-supplied filenames are never used as paths
   (stored under generated names, avoiding reserved names like `CON`/`NUL` and illegal characters).
8. **Windows file locking:** tests use `tmp_path`, close every handle before cleanup, and never delete an open file.
9. **Database tests need PostgreSQL** (Docker Desktop). If it is unreachable the suite **fails with a clear message**; it never
   silently skips database tests. Tests needing ffmpeg skip with a visible reason.
10. **Proxy-safe:** calls to `localhost` bypass system proxies (Windows reads them from the registry).
11. **One command to run everything** is documented and kept working, with the expected output stated.

## Risks being watched

1. **Gnani behaviour is unverified** (30 s limit, formats, Hinglish quality, concurrency). Mitigation: smoke test first, chunking and conversion built in, typed-report fallback.
2. **Scope vs five days.** Mitigation: the cut list and checkpoints above.
3. **Matching quality** on short, mixed-language text. Mitigation: structured signals carry most weight, labelled synthetic set with many negatives, lexicon review.
4. **Deployment** (ffmpeg, ephemeral disks, free-tier limits). Mitigation: Docker image, S3-compatible storage, local fallback demo.
5. **Testing environment limits:** I can run backend tests in my sandbox but not Docker; browser behaviour (microphone, mobile layout) can only be confirmed by you.
